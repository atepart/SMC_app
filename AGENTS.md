# Правила работы с AOCapp

Этот файл обязателен для всех разработчиков и AI-агентов, работающих в репозитории. Задача считается завершённой только после выполнения полного цикла разработки и проверки, описанного ниже.

## Команды и Python-окружение

- Перед **каждой** командой в терминале обязательно ставить `rtk`.
- Если команда состоит из нескольких частей, каждая часть должна иметь свой префикс: `rtk git add . && rtk git status`.
- Для диагностики допускается запуск без фильтрации только через `rtk proxy <команда>`.
- Не использовать системный `python`, `python3`, `pip` или прямой вызов `.venv/bin/python`.
- Python и Python-инструменты запускать только через `uv`:
  - приложение: `rtk uv run python -m aocapp`;
  - тесты: `rtk uv run pytest`;
  - отдельный тест: `rtk uv run pytest tests/test_file.py::test_name`;
  - линтер: `rtk uv run ruff check .`;
  - форматирование: `rtk uv run black .`;
  - проверка форматирования: `rtk uv run black --check .`;
  - импортов: `rtk uv run isort --check-only .`;
  - установка окружения: `rtk uv sync`;
  - добавление зависимости: `rtk uv add <package>`, dev-зависимости: `rtk uv add --dev <package>`.
- Не устанавливать зависимости глобально и не изменять окружение в обход `uv`.
- Любые новые команды в документации и скриптах для разработки должны соответствовать этим правилам.

## Источники текущей работы

Рабочая информация хранится в четырёх файлах:

- `docs/workplan.md` — только текущие и ближайшие согласованные задачи;
- `docs/bugs.md` — подтверждённые дефекты;
- `docs/backlog.md` — идеи и отложенные задачи без обязательства выполнить их сейчас;
- `docs/changelog.md` — завершённые и проверенные изменения.

Перед началом работы обязательно прочитать эти четыре файла. Они являются рабочим источником истины и должны обновляться вместе с кодом.

## Работа с `docs/workplan.md`

- В `workplan` держать только актуальные задачи: `В работе`, `Запланировано`, `Заблокировано`.
- Каждая задача должна иметь стабильный идентификатор вида `WP-###`, краткий результат и проверяемые критерии готовности.
- Перед изменением кода перевести ровно одну выбранную задачу в `В работе` и записать, что именно будет проверено.
- Не отмечать задачу выполненной по факту написания кода. Сначала пройти автоматические и ручные проверки.
- После успешной проверки удалить задачу из `workplan` и перенести её итог в `docs/changelog.md` в том же коммите, что и реализацию.
- Если задача заблокирована, указать конкретную причину, уже выполненные проверки и условие разблокировки.
- Если объём задачи заметно изменился, сначала обновить критерии готовности в `workplan`.

## Работа с `docs/bugs.md`

- Новый дефект записывать сразу после воспроизведения; не прятать известные дефекты в комментариях к коду.
- Идентификатор дефекта: `BUG-###`.
- Для каждого дефекта указывать:
  - краткое описание и влияние;
  - окружение;
  - точные шаги воспроизведения;
  - ожидаемый и фактический результат;
  - при наличии — путь к скриншоту, логу или traceback;
  - приоритет и текущий статус.
- Исправляемый сейчас дефект связать с задачей `WP-###` в `workplan`.
- После исправления и повторной проверки удалить активную запись из `bugs.md`, а результат и способ проверки перенести в `changelog.md` с сохранением номера `BUG-###`.
- Неподтверждённое наблюдение сначала исследовать; не оформлять его как закрытый баг без воспроизведения.

## Работа с `docs/backlog.md`

- Идентификатор записи: `BL-###`.
- В backlog хранить идеи, улучшения, технический долг и задачи, которые пока не взяты в работу.
- Для записи указывать ценность/проблему, примерный объём и известные зависимости.
- Backlog не является обещанием реализации и не должен смешиваться с текущим планом.
- При выборе записи в работу перенести её в `workplan` с новым `WP-###`, сохранив ссылку на исходный `BL-###`.
- Удалять запись из backlog только при переносе в работу, осознанном отказе или потере актуальности; причину отказа кратко фиксировать в changelog.

## Работа с `docs/changelog.md`

- Changelog ведётся вручную в формате `Keep a Changelog`: раздел `Unreleased`, затем версии/даты.
- Записывать пользовательский результат, а не перечень изменённых файлов.
- Использовать категории `Added`, `Changed`, `Fixed`, `Removed`, `Security` по необходимости.
- В каждой записи указывать исходный `WP-###`, а для исправлений также `BUG-###`.
- В changelog попадают только фактически завершённые и проверенные изменения.
- При релизе содержимое `Unreleased` переносить в раздел версии с датой `YYYY-MM-DD`, после чего создавать новый пустой `Unreleased`.

## Цикл выполнения задачи

1. Прочитать `workplan`, `bugs`, `backlog` и `changelog`; проверить `rtk git status`.
2. Выбрать одну задачу, уточнить критерии готовности и пометить её `В работе`.
3. Изучить затронутый код и сначала воспроизвести изменяемый сценарий или дефект.
4. Реализовать минимальное цельное изменение без посторонних правок.
5. Добавить или обновить автоматические тесты. Исправление бага должно иметь регрессионный тест, если это технически возможно.
6. Прогнать быстрые проверки во время разработки, затем полный pre-commit check.
7. Реально запустить приложение и вручную пройти затронутый пользовательский сценарий.
8. Сохранить подтверждающие скриншоты и записать результаты проверки.
9. Обновить рабочие документы: завершённую задачу убрать из `workplan` и перенести в `changelog`; закрытый дефект убрать из `bugs` и отметить в `changelog`.
10. Просмотреть итоговый diff и только после этого создать коммит.

## Автоматические тесты и pre-commit check

Минимальный набор перед каждым коммитом:

```bash
rtk uv run ruff check .
rtk uv run black --check .
rtk uv run isort --check-only .
rtk uv run pytest
rtk uv run python -m compileall -q aocapp backend
rtk git diff --check
rtk git status --short
```

- Если часть набора пока отсутствует или сломана на исходной ветке, это не повод молча пропускать её: зафиксировать факт и точный вывод в `workplan` или `bugs`, затем согласовать/выполнить исправление.
- Для расчётной логики проверять нормальный сценарий, граничные значения и обработку некорректного ввода.
- Для UI по возможности добавлять тесты сигналов, состояний виджетов и связки UI с use case, но они не заменяют ручную проверку.
- Нельзя ослаблять тесты, линтеры или критерии качества только ради зелёного результата.

## Реальная проверка приложения и интерфейса

- После изменения функциональности запустить настоящую программу командой `rtk uv run python -m aocapp`, а не ограничиваться импортом модулей или моками.
- Пройти затронутый сценарий как пользователь: открыть нужный экран, заполнить поля, нажать кнопки, проверить переключатели, диалоги, расчёт, график, preview, сохранение файла и сообщения об ошибках — всё, что относится к задаче.
- Проверить минимум один основной и один ошибочный/граничный сценарий.
- Визуально проверить отсутствие обрезанного текста, наложений, пустых областей, неверных размеров, проблем со скроллом, фокусом и масштабированием окна.
- Сделать скриншоты ключевых состояний до/после или результата проверки. Хранить постоянные артефакты в `docs/screenshots/<WP-ID>/`; временные снимки не коммитить.
- В записи changelog кратко перечислить ручные сценарии и указать пути к сохранённым скриншотам.
- Если окружение не позволяет открыть GUI, не считать UI-задачу полностью проверенной: отметить блокировку в `workplan` и не коммитить как завершённую без явного решения владельца проекта.

## Правила коммита

- Перед коммитом выполнить весь pre-commit check, ручной UI-сценарий и `rtk git diff --check`.
- Просмотреть `rtk git status --short` и `rtk git diff`; в коммит не должны попадать секреты, временные файлы, результаты расчётов, сборочные артефакты или несвязанные изменения.
- Один коммит должен содержать одну логически завершённую и проверенную задачу вместе с тестами и обновлением документации.
- Сообщение коммита писать в повелительном наклонении и отражать результат, например: `Add validation for S21 frequency range`.
- Не создавать коммит, если проверки падают или реальный пользовательский сценарий не пройден. Исключение возможно только по явному указанию владельца с документированием известных проблем.
- Не выполнять `push`, не создавать тег и не выпускать релиз без отдельного явного запроса.
